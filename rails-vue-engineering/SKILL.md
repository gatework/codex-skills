# Rails / Vue 工程判断

交付最小而完整的业务变化。先理解哪些行为必须保持，再选择写法；现代化的收益是更容易理解、验证和维护，而非使用更多新语法。

本 skill 可用于仅涉及 Rails 或仅涉及 Vue 的任务。只读对应部分。已有项目 skill 负责领域规则和工具入口，本 skill 提供取舍方法；不把案例的产品规则推广到其他应用。

## 从事实开始

确认目标仓库、当前工作树与用户要求，阅读相关调用方和测试。版本从运行时声明、锁文件、构建配置核对；命令从项目脚本和 CI 查找。保留用户未提交改动，不因调研需要重置、清理或改写项目。

区分三件事：源码说明**现在怎样运行**；需求和契约说明**应该怎样运行**；测试说明**哪些行为被验证**。三者冲突时追查原因，不把当前实现自动当作正确规范。

简单修改直接完成相关检查；跨层或高风险变更，先简要回答：

1. 谁在什么场景完成什么动作，成功的可观察结果是什么？
2. 服务端事实、用户草稿、查询条件和缓存分别由谁拥有？
3. 什么不能被破坏？哪个事务、条件、约束或版本保护它？
4. 失败、重复、并发和迟到结果分别怎样处理？
5. 部署后仍存活的旧数据、队列和调用方是否兼容？
6. 什么证据能推翻方案，而不只是证明成功路径？

## 实现与审查的共同底线

- `false`、`nil`、缺失、空结果、无权限、部分成功和未知结果各有业务含义；先查契约再转换。
- TypeScript 类型、strong parameters、模型 validation 和数据库约束解决不同问题，不能互相冒充。
- 把数据库已提交、任务已接受、任务已执行、外部效果已确认分开；不能由前一项推导后一项。
- 在提交状态前检查结果是否属于当前请求、身份、记录或执行尝试；中止请求不等于服务器撤销操作。
- 复用框架和项目已有能力；独立职责可以提取一次性 service/composable，共享抽象需要真实共同语义。简单 CRUD 无需强制增加层。
- 正确处理异常可以是重试、明确拒绝、保留旧数据或局部降级。不要用空集合或成功状态遮盖未知失败。
- 只为受影响行为选择测试，完成项目要求的门禁；不要为了 skill 的完整性扩大用户任务。

## 验证本 skill

维护本 skill 时读取 [验收场景](tests/scenarios.md)。[结构检查](scripts/check_skill.py) 检查元数据与本地引用；[示例检查](scripts/check_examples.py) 在临时目录执行随包示例，依赖由调用方显式提供，不自动安装软件或启动服务。它证明局部语义，不证明 Codex 的实际任务表现，也不证明生产可靠性。

交付先说明结果，再说明理由、验证与限制。代码审查先列可靠发现；没有证据支持的问题不报为缺陷。仅进行了源码阅读时，不写“测试通过”或“功能完成”。
