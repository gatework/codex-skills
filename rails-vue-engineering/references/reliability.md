# 异步、外部效果与恢复

用于后台任务、远端操作、快照同步和重试。数据库、队列与远端效果是独立故障边界。

## 提交与入队不是同一成功

**触发**：job 消费刚写入的记录，或 API 返回“已接受”。

**判断**：最外层事务何时提交？实际 queue adapter、job 类和配置是什么？入队被拒时抛异常、返回 `false`，还是先延迟到提交后？

**做法**：使用当前版本支持的 after-commit 机制；适用时使用 `ActiveRecord.after_all_transactions_commit`。仅在 service 内部 `transaction` 后调用 enqueue，不能保证调用者没有外层事务。对立即入队同时检查异常和 `false`；保留 job 实例时可读取 `enqueue_error`。对延迟入队，调用返回 job 仅表示已登记，不保证以后队列接受。

**边界**：after-commit 不消除“DB 提交后、入队前进程退出”的窗口；只有业务要求可靠完成时才需要 durable intent/outbox 与恢复扫描，不要求每个低价值后台任务都新建表。测试适配器与生产适配器的事务行为可能不同。

**验证**：正常提交、外层回滚、适配器异常、返回 `false`、callback 中止、提交后故障及恢复。批量扫描既要继续健康项，也要汇总暴露失败。[立即入队教学例](../examples/enqueue.rb) 不处理 deferred enqueue，不能直接放进事务内使用。

## 执行所有权与远端幂等分别保护

**触发**：worker 可重试、租约可过期、任务可被取消或重新认领。

**判断**：旧执行是否仍能写结果？本地取消是否真的取消远端？远端收到同一业务请求两次会怎样？

**做法**：短事务认领 → 锁外 I/O → 短事务比较执行版本并写结果。成功和错误结果都校验执行身份；定义过期恢复。远端支持时使用稳定业务幂等键；新的 attempt 不应自动生成新的业务键。

**边界**：fencing/attempt 检查只阻止旧 worker 改本地记录，不能阻止它已发出的远端请求。超时不证明失败；远端效果未知时保留待核实状态，通过查询/回执/人工处理收敛，不盲目换键重放。至少一次是重复处理的设计假设，不是每种队列配置都保证不丢任务。

**验证**：远端成功后进程退出、旧 worker 成功与报错晚到、新 worker 接管、取消发生在 I/O 中、永久拒绝和临时故障。需要真实锁/队列的属性不能用纯内存 mock 宣称已证明。

## 快照完整性与新鲜度是两个条件

**触发**：同步后会删除、标失踪或整体替换本地数据。

**判断**：空集合是权威的“确实没有”，还是请求失败、缺页、权限不足？快照属于哪个对象、配置和版本？更老的完整快照能否晚到？

**做法**：先验证原始行类型、标识、分页完整性、重复和父子关系，再进入短写事务；按同步粒度保留失败项旧数据，报告部分成功。锁内重检对象身份及必要的 generation/revision。

**边界**：锁内重检 IP 只证明目标地址未变，不能证明快照比另一并发同步更新。上游若无一致快照版本，要明确其限制并选择串行同步、代次或有条件更新；不能凭总页数未变化宣称快照一致。

**验证**：非法类型、缺页、真实空快照、重复 ID、孤儿、配置变更、旧快照晚到和一个失败项旁的健康项。只有成功且完整的结果才有资格驱动缺失删除。

## 失败处理表达结果，不隐藏事实

**触发**：批处理、降级、catch/rescue 或清理流程。

**判断**：错误是否可恢复？哪些副作用已发生？重试会扩大损害吗？谁能观察失败？

**做法**：可预期拒绝形成明确业务结果；基础设施失败保留重试/告警语义；可丢弃投影降级但不升级为授权依据。秘密在日志和异常摘要落地前过滤。需要通知与宽限期的破坏性流程，把成功证据和 deadline 持久化后再推进。

**边界**：有意的局部降级可以捕获异常；不能因“禁止吞错”而让非关键缓存故障中断主业务。不要给所有清理动作强加提醒策略，也不要把 HTTP 4xx 一概看作首次请求未执行的证明。

**验证**：断言失败后的数据、返回值、队列与用户状态，而非只断言 rescue 分支被调用。
