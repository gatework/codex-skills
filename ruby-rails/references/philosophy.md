# 编程思想与可复用方法论

本文回答"为什么这样写"。先读思想,再遇到具体细则时才知道何时该变通。

目录:一、Ruby 的设计观 · 二、Rails 的设计观 · 三、十个可复用的方法 · 四、何时不该套用

## 一、从 Ruby 学到的设计观

**1. 为人设计,遵循最小惊讶。**
Ruby 的方法名就是契约:`empty?` 返回布尔,Active Record 的 `find` 缺失会抛、`find_by` 缺失返回 `nil`；Enumerable 的 `find` 默认返回 `nil`,`save!` 失败会抛而 `save` 返回 `false`。写自己的 API 时延续这套语义——读者看到名字就该猜对行为。
落地:谓词以 `?` 结尾并返回布尔;`!` 只表示"比普通版本更危险或失败约定不同";同一领域用同一个词,不要让同一对象在相邻层里轮换叫 record/item/entity。

**2. 一切皆对象,一切皆消息。**
调用者只依赖"对象能响应什么消息",不依赖它的类。这是鸭子类型的根基。
落地:内部协作者按方法协议协作,不到处 `is_a?`;数据边界处才验证真实类型和形状。

**3. 块把"变化点"交给调用者。**
`File.open`、`transaction`、`each` 都是同一个模式:方法掌管流程与资源,块提供每次不同的部分。
落地:资源型 API 提供块形式并在 `ensure` 中释放;自定义迭代无块时返回 `Enumerator`;重复出现的"前后包裹"逻辑写成接收块的方法(`with_retry`、`with_lock`)。

**4. 模块复用"能力",继承复用"是一种"。**
`Comparable`、`Enumerable` 只要你提供 `<=>` / `each` 就给你几十个方法——这是 mix-in 的典范:小接口换大能力。
落地:共享的小型能力用模块并写明宿主需提供的方法;真正的 is-a 才用继承;不为藏复杂度而叠模块与回调。

**5. 开放与动态是能力,不是默认方案。**
开放类、`method_missing`、`eval` 让 Rails 的 DSL 成为可能,同时把"发现成本"转嫁给读者。
落地:先用普通组合表达;确需动态时遵循 [metaprogramming.md](metaprogramming.md) 的阶梯。

**6. 表达力优先于短。**
函数式链适合数据变换,顺序步骤适合控制副作用。选读者能追踪的数据流,而不是最短的一行。

## 二、从 Rails 学到的设计观

**1. 约定优于配置 = 少做无意义的决定。**
`Order` 自动对应 `orders` 表、`order_id` 外键、`OrdersController`、`app/views/orders`。这些推导让团队把注意力放在业务差异上。
落地:优先使用默认命名；项目已有的配置化命名同样有效，偏离默认时应能解释其业务或兼容性原因。

**2. DRY 是"知识的单一来源",不是文本去重。**
两段长得一样但代表不同业务规则的代码,合并后会被迫一起变化(偶然重复)。同一规则可能需要在 UI 提示、应用校验和数据库约束中分别执行；这属于不同边界的保护。集中规则定义或用契约测试保持一致，不为消除文本重复而删除数据库约束或服务端校验。
落地:合并前问"这两处会因为同一个原因变化吗?"

**3. 用整套默认工具。**
ActiveJob、ActionMailer、credentials、I18n、`Rails.cache` 能解决时,不引入平行方案。评估替代品要把接入、排障、升级、交接成本一起算。

**4. 资源导向。**
有独立生命周期的取消、审批可以建成资源，如 `resource :cancellation`；简单动作也可以是 member action。选择看业务含义、权限边界与现有路由，不为保持 CRUD 外形制造对象。

**5. 富模型不等于巨模型。**
业务行为放模型是 Rails 的本意;问题在于把不相干的职责堆一起。拆分依据是职责和依赖：Concern 可组织宿主的一项能力，需要独立状态或依赖时用对象；两者都不是文件过长的自动处方。

**6. 开发者体验是质量的一部分。**
错误信息、命名、`rails console` 可探索性、测试反馈速度都算。领域入口应便于在测试或 console 中探索，并明确所需授权上下文和副作用。

## 三、十个可复用的方法

每个方法给出:何时用 → 怎么做 → 怎么检验。

### M1 契约四问

- **何时**:任何改动之前,尤其是改公共方法、写新 API、重构。
- **做法**:写下 ①输入(含非法输入) ②输出/返回值 ③失败如何表达(异常类型?`nil`?错误对象?) ④副作用(库、队列、缓存、外部服务)。再补 ⑤重复或并发调用会怎样。
- **检验**:每一问都能指到一个测试或一段代码。写不出来说明需求或设计不清,先澄清而不是先编码。

### M2 抽象成本账

- **何时**:想加新类/层/Concern/DSL/依赖时。
- **做法**:比较真实调用点,回答三问:
  1. 它能集中"会一起变化的东西"吗?
  2. 它能表达并守住一个不变量吗?
  3. 它能隔离外部协议(HTTP、SDK、文件格式)吗?
- 三问全否 → 不加。仅转发同名 CRUD、增加导航步数的层,成本大于收益。
- **检验**:删掉这个抽象后调用点会变得更难理解吗?不会就别留。

### M3 阶梯升级

- **何时**:在"简单办法"与"强大机制"之间选择。
- **做法**:从最简单可行的办法开始,只有它明确不够时才升一级,并在代码或提交说明里写下"为什么不够"。适用于元编程(见阶梯)、并发（线程池解决受控并行，持久队列解决异步与恢复，不是同一条性能升级路径）、缓存(不缓存 → 局部 memo → `Rails.cache`)、抽象（方法、Concern、独立对象按职责选择，并非固定升级链）。
- **检验**:能说明新增机制解决了什么真实约束，而不是把工具排成必经顺序。

### M4 最小贯通与证据驱动的抽象

- **何时**:新增能力,尚不确定抽象形状。
- **做法**:先贯通一条最小的真实路径(路由 → 控制器 → 模型 → 视图/JSON → 测试),看得到结果再抽。重复次数只是信号；集中一个关键不变量可在首次出现时抽取，碰巧相似的多段代码也不必合并。
- **检验**:抽取后职责更清楚，调用契约不变，且新增跳转成本有收益。

### M5 在边界解析,在内部信任

- **何时**:数据跨越信任边界(请求参数、外部 JSON、文件、队列消息)。
- **做法**:在边界一次性把外部值变成受信任的形态(类型、范围、枚举、必填),失败就拒绝并保留证据;内部方法依赖已建立的保证,不重复兜底。不要用 `to_i`/`to_s`/`!!` 把非法值静默变成"合法的零/空串/布尔"。
- **检验**:非法输入是否产生了明确错误,而非默默变成默认值?

```ruby
# ✗ "abc".to_i == 0,非法输入变成合法的 0
page = params[:page].to_i

# ✓ 边界处解析并拒绝
raw = params.fetch(:page, "1")
raise ArgumentError, "invalid page" unless raw.is_a?(String) && /\A[0-9]+\z/.match?(raw)
page = Integer(raw, 10)
raise ArgumentError, "page 必须 >= 1" if page < 1
# 在这个解析边界翻译为项目的输入错误；不要全局把任意 ArgumentError 当成客户端错误
```

### M6 状态显式化

- **何时**:对象有生命周期(订单、同步任务、审批)。
- **做法**:用枚举表示状态,用具名方法表示转换(`cancel!`、`ship!`),在方法内校验"当前状态是否允许",并让数据库约束保护底线。为"未知/尚未评估"保留独立状态,不要与"空/否"混用。
- **检验**:非法转换会失败且不留下半成品数据。

### M7 纯核心,命令式外壳(Functional Core, Imperative Shell)

- **何时**:业务规则与 I/O 缠在一起,难以测试。
- **做法**:把计算、判断、格式化写成不碰网络/文件/数据库的纯方法;由外壳(控制器、job、use-case)负责读取输入、调用纯核心、写入结果。查询方法不产生持久副作用(命令/查询分离)。
- **检验**:核心规则能不启动数据库直接单测。

```ruby
# 纯核心:只算,不写
module Pricing
  # 金额用整数最小单位(分),比例用整数基点(1% = 100 bps),不用浮点算钱
  def self.total_cents(items, discount_bps:)
    subtotal = items.sum { |item| item.unit_cents * item.quantity }
    Rational(subtotal * (10_000 - discount_bps), 10_000).round   # 精确有理数;取整规则由业务确认
  end
end

# 命令式外壳:读取、调用、写入
def checkout!(cart)
  cents = Pricing.total_cents(cart.items, discount_bps: cart.customer.discount_bps)
  cart.create_order!(total_cents: cents)
end
```

### M8 重构安全网

- **何时**:保持行为的重构。
- **做法**:①列出必须保持的可观察行为(返回值、异常、副作用、加载路径) ②缺测试则先写特征测试固定现状 ③小步移动/重命名,每步可运行 ④验证 autoload、参数/块转发、兼容入口。格式化与行为修改分开提交。
- **检验**:外部行为未变;没有夹带功能变更。

### M9 名字即设计

- **何时**:起名困难时。
- **做法**:找不到不含 `And`/`Manager`/`Helper`/`Processor` 的名字,通常意味着职责混杂。用领域动词命名动作(`cancel`、`reconcile`),用领域名词命名对象(`Invoice`、`PolicyParser`)。变量带上形状与单位:`users_by_id`、`timeout_seconds`、`max_bytes`。
- **检验**:不看实现,只读名字,能猜对行为与返回。

### M10 删除优先,证据交付

- **何时**:每次收尾。
- **做法**:先删无调用代码、复用框架原语,再考虑新增。交付时区分"已证明/未证明":lint 通过不等于授权正确,入队成功不等于任务执行,mock 通过不等于真实服务可用。
- **检验**:报告里每个"已完成"都指向一条实际执行过的检查。

## 四、何时不该套用

- 项目已有明确约定(目录、命名、service 惯例、120 列、单引号、RSpec):沿用,新代码与多数一致,旧代码随相关修改渐进调整。
- 一次性脚本与原型:不必套用分层与完整测试,但仍遵守边界解析与破坏性操作的安全底线。
- 规则与实测冲突时,以目标版本的实际行为为准,并把结论写进提交说明。
