# Ruby & Rails 工程技能

让代码表达业务意图，让框架机制服务于可验证的行为。区分**必须保持的契约、按场景选择的设计、由项目决定的风格**，不要把偏好写成通用禁令。

## 开始工作

- 先定位实际项目根目录，查看工作区状态、项目指令、运行时与锁文件、`load_defaults`、加载配置、测试和 CI 入口；保留已有改动。小修只读相关路径，不做整仓审计。
- 找相关调用者和同类实现，确认输入、输出、失败、副作用，以及重复或并发执行的契约。信息可以从代码发现时先查；有影响数据模型或公共 API 的歧义时再问。
- 优先复用模型、框架和已有对象。新层应集中业务知识、保护不变量或隔离外部协议；方法数量、文件长度和重复次数本身不决定抽象。
- 缺陷用能复现的回归固定行为；重构保持参数、返回、异常、资源所有权和加载契约。格式修改不夹带行为变化。

## 核心不变量

1. **边界解析不掩盖错误。** 区分缺失、`nil`、`false`、非法与未知；参数允许列表、类型转换、业务校验和授权各有职责。
2. **授权覆盖对象、动作和字段。** 从可见范围查找后仍须判断能否执行该动作；后台任务、导出和附件同样要明确授权上下文。
3. **一致性取决于真实边界。** 数据库约束与锁/条件更新可以组合；局部事务块结束不代表外层提交，数据库事务也不能回滚远端效果。
4. **阶段分别报告。** 持久意图、入队、执行、外部效果确认不是同一事实。关键异步工作需要可恢复状态；超时可能意味着结果不明。
5. **项目契约优先。** 使用目标版本支持的 API，沿用已有测试框架、目录、风格和队列。发现真实风险时给出证据，不静默改变已发布行为。

## 工作尺度与交付

概念问答直接解释；小修验证相关行为；跨层业务改动验证贯通路径与失败恢复。审查默认报告位置、触发条件、影响与修复方向；用户已授权修复时继续完成。没有仓库或运行环境时说明假设，不假装勘察或执行。

执行共享环境、破坏性或发布操作前核对目标和现有授权；授权不足才请求确认，不重复索取已有授权。勘察不自动授权重写项目规范或修改其他项目。

使用用户的语言交流，代码注释、文档及提交信息沿用项目习惯。交付说明改变了什么、为什么，以及实际命令和结果；通过、失败、环境阻塞与未执行分别报告。mock、静态检查和入队断言只证明各自边界，不代表真实服务或完整版本矩阵验收。
