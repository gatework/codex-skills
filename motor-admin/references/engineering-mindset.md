# 工程思想：从不变量到证据

设计新功能、评审方案取舍、做跨层变更或判断“该不该抽象”之前读取本文件。它把 Motor 分散在各 reference 的具体规则抽象成一套可迁移的思考方式：遇到规则没有覆盖的新情况时，用这里的原则推导，而不是凭感觉。

原则是推导工具，不是新的硬性规则。源码说明当前行为，契约说明预期，测试说明覆盖；冲突时追查而非自动接受当前实现；与安全、数据、发布边界冲突时，以对应 reference 为准。

## 一次变更的七问

动手前用几句话回答，简单任务一行即可，复杂任务写进方案。答不出来说明还没理解问题，不是要多写代码。

1. **任务**：谁在什么场景下完成什么，怎样算完成？
2. **权威**：这件事的权威事实在哪（PostgreSQL、后端授权、服务端 session），哪些只是投影（Redis、前端权限、缓存、URL）？
3. **不变量**：用一句话写出“无论怎样都不能被破坏的事”，包含全局不变量（最后一个管理员、唯一 active 配置）。
4. **失败方向**：出错、重复、并发、崩溃、依赖不可用时，往哪个方向失败（fail-closed / 降级 / 可重试）？
5. **存活表面**：部署后哪些东西还活着（队列里的旧 job、旧前端、持久化的 permission key、外部调用者）？
6. **最小完整变更**：现有原语和 Motor 抽象能否直接表达？缺的是什么？
7. **证据**：什么测试或运行结果能证明不变量成立，且在旧实现上会失败？

## 九条核心原则

### 1. 不变量先行

先写不变量，再写代码。不变量决定数据约束、事务边界、锁的位置和测试断言；页面按钮、controller action 只是入口。

- Motor 体现：禁用不等于删除；API Token 权限是 scope 与角色当前权限的交集；destructive 流程要“证据在前、宽限期在后”。
- 检验：能否把这次变更的核心风险写成一句“任何时刻都不允许……”？
- 反模式：从 UI 或 CRUD 模板出发，写完才发现没有地方表达“至少保留一个管理员”。

### 2. 单一权威，其余皆投影

每个事实只有一个权威来源，其余都是可重建、可丢弃的投影。能推导的不存储，能重新读取的不缓存成第二真相。

- Motor 体现：PostgreSQL 是用户/角色/会话/通知/投递的权威；Redis 在线状态、前端权限、tabs、Cable 订阅都是投影。前端 query state 是请求参数、页面显示和分页的唯一来源。
- 收敛规则：权威变化后，投影要么被重建，要么被清除，不能靠“再同步一次”。身份变化是状态迁移，不是换 token。
- 检验：投影丢失或过期时，系统是降级还是越权？
- 反模式：用 Redis 里的旧状态继续授权；页面 ref、table 内部分页和 API 参数各存一份 current page。

### 3. 让非法状态难以表示

在最靠近数据的地方拒绝非法状态，越早越便宜。

- 数据库：NOT NULL、UNIQUE、CHECK、FK、部分索引保护持久化事实；model validation 提供可理解的错误。两层同时存在，各司其职。
- 后端：排序/枚举/状态用 allowlist；简单转换可用条件 UPDATE，需要领域生命周期时可用锁内重检与更新，避免无保护的先读后判。
- 前端：互斥阶段可用判别联合并检查穷尽；刷新、旧数据与独立行级提交可以同时存在，不强制一个巨型状态机。
- 反模式：`isLoading` + `hasError` + `isEmpty` 三个独立布尔值，可以同时为真。

### 4. 失败方向是设计决策

“出错时怎么办”要在设计阶段决定，不能留给 `rescue` 的默认行为。

| 状态类型 | 失败方向 |
| --- | --- |
| 授权、认证、destructive 前置条件 | fail-closed：不确定就拒绝或不执行 |
| 可重建投影（在线状态、缓存、Cable） | 降级：功能变弱，不影响授权判断 |
| 外部 provider 临时失败 | 可重试：保留 durable 状态，抛出让队列重试 |
| 业务上预期的失败 | 稳定状态与 `code`：不重试、不吞掉 |

- 检验：这个 `rescue` 之后系统处于哪种状态，是否伪装成成功？
- 反模式：`rescue nil`、空 catch、把未知错误映射成 422 或 200。

### 5. 在边界解析，在内部信任

数据进入系统的边界统一解析并收窄类型，内部代码基于已解析的结果工作，不到处重复校验。

- 边界：strong params 的允许列表、外部原始数据的运行时校验、表单 encode/decode、job 参数协议。`ApiResponse<T>` 和 serializer 本身不是运行时输入验证器。
- 表单 UI model 与 API payload 不同形时，用局部纯函数 `decode → FormModel → encode`，不在 submit handler 里散拼。
- 检验：内部函数是否在猜测参数形状？错误是否在边界处就变成了稳定 `code`？
- 反模式：前端解析 Ruby 异常文案；controller 里到处 `params[:x].present?` 后各自处理。

### 6. 副作用显式，命令与查询分离

纯的决策/转换和有副作用的编排分开：核心逻辑尽量是可单测的纯函数或小型 model 操作，外壳负责事务、I/O、入队和广播。

- Motor 体现：跨系统副作用放在明确的 service 流程，不藏进 model callback；查询方法不改状态，命令方法名带动作语义。
- 副作用的顺序要可追踪：`commit → enqueue → provider → result`，每一步失败后系统处于哪里，必须说得清。
- 反模式：`after_save` 里发 HTTP；名叫 `find_xxx` 的方法顺手改了记录。

### 7. 至少一次与幂等

分布式副作用默认“至少一次”。不要追求 exactly-once，要让重复执行无害。

- Motor 体现：job 参数保持可序列化且最小，通常传 ID 后重读；必要时保存经保护的执行快照，有稳定 delivery/event ID 作幂等键或去重键；一次性 credential 用带条件的原子消费。
- provider 没有幂等能力时，承认重复窗口，用审计和 reconciliation 覆盖，不假装事务能消除远端副作用。
- 检验：同一个 job 跑两次会怎样？worker 在远端成功后崩溃会怎样？
- 反模式：先读再判再写的“一次性消费”；用进程内标志位当去重。

### 8. 兼容窗口：expand → migrate → contract

持久或外部表面存在旧消费者时，需要兼容窗口再收缩；确认无旧消费者的内部变化不必制造兼容层。

- 三类表面：内部实现（可原子改）、持久兼容表面（DB 数据、permission key、job class、cache key）、外部契约（route、JSON 字段、env、镜像 tag、深链）。
- 全仓 grep 只能证明源码里没人引用，证明不了队列里的旧 job、旧数据、外部调用者不再依赖。
- 兼容层要有用途、验证方式和退出条件，不做永久 alias。
- 反模式：一次改名同时改 controller、permission key 和 DB 数据，部署窗口内旧 worker 直接失败。

### 9. 证据高于断言

“应该没问题”不是完成。完成 = 契约保持 + 可复现的验证 + 明确列出的未验证项。

- 回归测试优先在旧实现上失败、修复后通过；并发用可控 barrier，不用“多跑几次”。
- 绿色必须真实：不接受全 skipped、空输入、no-op 后返回 0；build 成功不等于运行过 production artifact。
- 报告只写本次真正执行或读取的证据，并区分“源码阅读”“自动门禁”“真实运行”“未验证”。
- 反模式：用 CI 全绿宣称 production-ready；没开浏览器就写“UI 已确认”。

## 现代范式对照

下表说明常见范式在 Motor 中落在哪里、什么时候才值得采用。范式是手段，只有对应问题真实存在时才引入。

| 范式 | 在 Motor 中的落点 | 采用条件 |
| --- | --- | --- |
| Functional core, imperative shell | 纯 codec/决策函数 + service 编排事务与 I/O | 逻辑有分支且需要单测时；简单保存不必拆 |
| Parse, don’t validate | 原始输入的运行时解析、允许列表、表单 codec；类型声明不替代校验 | 数据跨越信任或类型边界时 |
| Compare-and-set / 乐观并发 | 条件 UPDATE + 受影响行数、`lock_version` | 状态只能从 A 到 B、客户端编辑冲突 |
| 幂等键 / 去重键 | delivery ID、event ID、dedup key | 任何可能被重试的外部副作用 |
| Durable intent（outbox 思想） | 持久派发意图与恢复扫描；不要求两张表 | 副作用必须在崩溃后可恢复、可审计时 |
| Expand / contract | 危险 migration、rename、route/JSON 变更 | 有旧新代码共存窗口时 |
| Contract-first | `{ data, meta }`、`code + message`、permission catalog | 前后端或外部方共同依赖时 |
| 判别联合状态机 | `RequestState`、Drawer 生命周期 | 有多个互斥阶段的异步 UI |
| 派生状态优于存储 | computed、query state 推导请求参数 | 值可由已有状态计算时 |
| 优雅降级 | Cable 失败回退 HTTP；Redis 投影失败不影响授权 | 存在可重建的辅助能力时 |
| 最小权限 + 纵深防御 | token scope ∩ 角色权限；后端为权威、前端为投影 | 所有敏感动作 |
| 组合优于继承 | composable、单一职责 Concern、Arco 原语组合 | 需要复用行为而非复用类型时 |
| 相关性关联（correlation） | request_id → actor → target → job/delivery | 需要跨异步边界排障和审计时 |

不要因为范式流行就补齐：没有崩溃恢复需求就不建 outbox 表，没有第二个调用方就不抽 schema 引擎。

## 抽象是否赚回成本

新增层、公共 helper、依赖或配置前，依次通过下面四个检验：

1. **追踪检验**：沿一次真实调用追踪输入、状态和失败。新层只增加跳转、读者仍要理解全部底层细节，则收缩。
2. **删除检验**：删掉它，调用方是变得更难理解，还是只是多写几行？后者不值得保留。
3. **调用方检验**：有真实共同语义，或一个明确独立的生命周期；提取能够减少契约漂移、状态耦合或理解成本。
4. **半径检验**：需求变化时，改动是集中在一处，还是仍要同时改抽象和所有调用方？

阶梯：框架/项目已有原语 → Motor 已有 model/service/query/serializer/composable/component → 现有层内的小能力 → 第二个真实调用方后提取 → 只有现有架构无法表达才引入新公共层或依赖。

配置面同理：正确默认值优先；差异来自业务实体就显式建模；只有真实、长期并存的运维策略才做配置，并写清作用范围、默认值和维护责任。

## 反模式速查

| 反模式 | 为什么危险 | 替代做法 |
| --- | --- | --- |
| 前端权限当安全边界 | 绕过 UI 即越权 | 后端 route/action 授权为权威，前端只做投影 |
| `transaction` 当并发锁 | 不同记录上的事务不会互相串行 | 锁稳定 anchor、条件 UPDATE、advisory lock、唯一约束 |
| 持 DB 锁做网络 I/O | 长锁、连接池耗尽 | claim → 释放锁 → I/O → 写结果 |
| model callback 藏跨系统副作用 | 回滚、测试、排障都不可见 | service 中显式编排，明确 commit boundary |
| 直接整列覆盖聚合字段 | lost update、擦除未回显 secret | 走既有聚合封装（如 `Motor::UserSettings`） |
| 用展示文案做程序分支 | 翻译或改文案即破坏逻辑 | 稳定 `code` / `key` / `event_type` |
| 首轮既提醒又执行 destructive | 用户没有申诉或恢复窗口 | 持久化通知与 deadline，宽限期后重检再执行 |
| 为统一而重写已正确的交互 | 引入回归、丢失既有能力 | 先修 correctness 和信息层级，再谈抽象 |
| 引入第二套基础设施 | 两份状态来源、两套维护 | 复用现有 HTTP client、权限模型、页面 shell、token 系统 |
| 用数量当证据 | “跑了很多次没失败”不证明竞态已消除 | 确定性 barrier 测试 + 旧实现失败证明 |
