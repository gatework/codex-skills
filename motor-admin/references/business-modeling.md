## 方法总览

```text
用户任务 -> 动作卡 -> 状态流 -> 权限四问 -> 收敛检查 -> 失败方向 -> 测试矩阵
```

页面、API、表结构都是这条链的产物，不是起点。身份、安全和 destructive 流程的状态流比 CRUD 结构更重要；普通配置类 CRUD 可以把动作卡缩成三五行。

## 动作卡

每个会改变状态的业务动作，先填一张动作卡。任何一项答不出，先补需求再写代码。

```text
动作：<动词 + 对象>
发起者与凭证：<哪些角色 / credential type 可以发起；API Token 是否允许>
前置条件：<权限、当前状态、配额、目标范围、防提权>
权威状态与转换：<from -> to；哪一步必须原子；序列化点在哪>
不变量：<一句话，含全局不变量>
副作用：<同步 / 异步；可重试还是可重复；provider 是否有幂等键>
撤销与收敛：<哪些 credential、session、projection、前端状态要失效或重建>
审计：<actor、target、event 标识、结果>
失败方向：<fail-closed / 降级 / 可重试；用户看到什么、下一步做什么>
兼容表面：<route、permission key、字段、job、队列、env>
验证：<证明不变量的测试；并发与重复怎么测>
```

## 状态流建模

用文本状态图描述，重点是**非法转换如何被拒绝**，而不是画得好看。

```text
[active] --disable--> [disabled] --enable--> [active]
   |                       |
   +-- delete (blocked if history exists) --> [deleted]
```

对每条边写清：

- **守卫**：谁可以触发，需要什么前置状态与条件；
- **原子点**：用条件 UPDATE + 受影响行数，或对稳定 anchor 加锁；
- **副作用**：转换成功后必须发生什么，失败时保留哪些 durable 证据；
- **不可逆性**：是否需要确认、预览或宽限期。

区分三种状态：**业务状态**（active/disabled，持久权威）、**流程状态**（pending/sending/delivered，用于 claim 与重试）、**展示状态**（loading/error，只在 UI）。不要把它们塞进同一个字段或同一个布尔值。

## 权限四问

任何敏感动作，逐一回答：

1. **谁**：actor 是谁？用户代入时，真实 actor 与 target 分别是谁？
2. **对谁**：actor 能否操作这个 target（防提权、超级管理员保护、自我操作限制）？
3. **凭证**：允许哪些 credential type（浏览器 JWT、API Token、代入 JWT、Admin session）？
4. **范围**：数据范围由后端决定，不接受前端传入“允许的 ID 列表”。

并验证：actor 当前的**活动角色**是否有该动作权限；能否授予高于自身有效权限的能力；并发的角色变化后旧请求是否仍能写入。

前端权限只做体验投影：route meta、菜单、按钮引用与后端相同的稳定 permission key，通过统一 ability 入口判断。

## 权威变化的四层收敛

任何改变“用户能做什么”的动作（改密码、禁用、角色切换/变更、Token 撤销、代入开始/结束、MFA 变化），逐层检查：

| 层 | 问题 | 典型遗漏 |
| --- | --- | --- |
| 数据库权威 | session / token / role / status 是否已更新 | 只改了展示字段 |
| Credential | 旧 JWT / API Token 是否还能用，是否轮换或撤销 | 换了新 token 但旧 token 仍有效 |
| 投影 | Redis 在线状态、Cable 订阅、缓存是否清理 | 旧订阅继续收到新身份不该看的事件 |
| UI | route、tabs、页面数据、在途请求是否按新身份重算 | 旧身份请求晚到，污染新身份状态 |

四层缺一，都不算完成收敛。

## 语义矩阵：禁用、撤销、归档、删除

这四个动作经常被 CRUD 的“删除按钮”混为一谈，先决定语义再设计接口：

| 语义 | 含义 | 历史保留 | 典型对象 | 可恢复 |
| --- | --- | --- | --- | --- |
| 禁用 | 阻止继续使用，保留实体 | 保留 | 账号、配置、渠道 | 是 |
| 撤销 | 使某个 credential 失效 | 保留记录 | session、API Token | 否（重新签发） |
| 归档 | 从活动视图移走，不改变事实 | 保留 | 通知 | 通常是 |
| 物理删除 | 抹除数据 | 由 retention 规则决定 | 无审计价值的子数据 | 否 |

有日志、会话、Token、投递或审计价值的记录，默认阻止级联硬删除，用稳定业务冲突（如 409）告知阻塞原因。

## 稳定标识与展示文案

程序分支、审计、契约依赖**稳定机器标识**，不依赖**展示文案**：

| 稳定标识（不可随文案变） | 展示内容（可翻译、可调整） |
| --- | --- |
| `username`、permission key、dictionary `code` / entry `key`、`event_type`、错误 `code`、配置 key | 显示名、菜单标题、字典 `label` / `description`、错误 `message`、通知标题 |

判断方法：如果改一个文案会让某段逻辑或某条审计记录失效，说明用了不该用的字段做标识。未知的字典值要安全降级显示，不能让页面崩溃。

## 事件、通知与投递的分层

```text
business event -> durable notification / dispatch intent -> queue -> provider / in-app projection
```

- 业务代码发布事件，不直接依赖某个邮件或 Webhook provider；
- 通知（读/归档）与投递（成功/失败）是不同状态，互不替代；
- 同一业务执行按需要使用稳定 dedup key；派发载荷只保存必要快照并保护秘密，先读当前 publisher/job/schema，不假定存在独立 delivery 表或渠道回执；
- provider 与 Cable 是副作用或投影，可以失败、重复、延迟。

**何时不需要这么重**：只在本进程内、丢失也无害的提示（例如页面 toast）不必建 durable 记录。分层是为“崩溃后可恢复、可审计”付费，需求不存在就不引入。

## 破坏性流程模板

项目明确要求预先通知与宽限期的自动禁用、日志清理适用以下骨架；普通批量删除按自己的产品契约设计：

```text
资格判定 -> 前置证据 -> 通知成功 -> 持久化 notice 与 deadline -> 宽限期 -> 重检安全不变量 -> 执行 -> 审计
```

三个必答问题：

1. **缺前置能力时怎么办？**（没有可通知的管理员、通知渠道不可用）→ fail-closed，不继续。
2. **首轮扫描能否同时提醒并执行？** → 不能，首轮只建立证据和 deadline。
3. **到期后是否重新检查？** → 必须；资格、最后管理员、活动状态、保留义务都可能已变。

批量执行分批，避免长事务；审计里能解释“为什么现在执行”。外部通知 I/O 与数据库锁的冲突，见 [business-workflows.md](business-workflows.md#外部通知与数据库锁的冲突)。

## 审计的最小字段集

- request / job 关联 ID；
- 真实 actor 与 target（代入时二者不同）；
- credential 与代入上下文；
- 稳定的 action / event 标识；
- 时间、结果、必要的安全摘要（先脱敏，再持久化）。

原则：归档、撤销、禁用优先于抹除历史；物理删除有独立 retention 规则和操作证据；不能通过运维后台修改只读审计历史。

## 业务错误模型

- **预期业务错误**：稳定 `code` + 可翻译 `message`（必要时附字段级 `errors`），前端按 `code` 选交互；
- **意外错误**：不暴露内部细节，进入统一异常通知；
- **异步**：预期失败写成业务状态，临时失败抛出让队列重试；
- **用户可见结果**：每个失败要说清“发生了什么、影响什么、下一步做什么”；
- **不泄漏**：不通过错误差异泄露账号是否存在、challenge 内部状态或 secret。

## 需求澄清清单

需求不足以填完动作卡时，优先自己读源码、schema、测试回答；确实只有用户知道时，一次问最关键的一两个问题，附上你的默认假设，方便用户只回答“对/不对”。常见的高价值问题：

- 这个动作是否可逆？误操作的代价是什么？
- 有历史数据（日志、会话、Token、投递）的对象，删除时期望阻止、级联还是归档？
- 并发发生时，允许“最后写入胜出”，还是必须拒绝其中一个？
- 重复执行（重试、重复点击）时，期望幂等还是产生两条记录？
- 谁能看到、谁能操作？API Token 是否也允许？
- 异步动作完成前，用户应该看到什么状态？失败如何回看？

## 完整示例：禁用用户

以下是用动作卡分析“禁用用户”的过程，展示方法，实际细节以目标 ref 为准。

```text
动作：禁用用户
发起者与凭证：有对应 permission 的浏览器会话；API Token 默认不允许（账户管理属于安全能力）
前置条件：actor 当前活动角色有权限；target 不是超级管理员；不是自我禁用；防提权检查通过
权威状态与转换：enabled -> disabled，沿当前领域操作锁内重检并撤销凭证；
               全局不变量“至少一个有效管理员”需要所有竞争者争用同一序列化点
不变量：任何时刻至少存在一个可用管理员；disabled 用户的所有认证方式都被拒绝
副作用：撤销该用户的 session 与 API Token；清理 Redis 在线投影；断开 Cable 订阅；
        发布“账号被禁用”事件（可重试，可重复）
撤销与收敛：DB 状态 -> credential -> 投影 -> UI（被禁用者下次请求 401；操作者列表刷新）
审计：actor = 操作者，target = 被禁用用户，event_type 稳定，记录结果与请求关联 ID
失败方向：无法确认最后管理员保护 -> 拒绝（fail-closed）；投影清理失败 -> 降级，不恢复 DB 已撤销的会话
兼容表面：permission key、事件类型、API 错误 code（如 last_admin_required）
验证：双连接 barrier 测试（两个管理员被同时禁用）；旧 token 被拒；代入场景的 actor/target；
      前端身份收敛（被禁用者当前页面）
```
