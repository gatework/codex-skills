## 来源与使用边界

依据 Arco 官方规范的四篇正文整理：

- [介绍](https://arco.design/docs/spec/introduce)：设计语言与设计系统的职责。
- [设计价值观](https://arco.design/docs/spec/values-of-arcodesign)：清晰、一致、韵律、开放。
- [设计原则](https://arco.design/docs/spec/philosophy)：八项面向使用过程的原则。
- [样式指南](https://arco.design/docs/spec/style-guideline)：色彩、文字、阴影、文案样式和用语。

正文核读依据为 [Arco 官方文档源文件](https://github.com/arco-design/arco-doc-site/tree/b4e5d6d9f3106a1205eecd9057bd93997846e27d/docs_spec)。链接中的 ref 仅用于追溯来源，不代表 Motor 的版本要求；官网更新或需要精确数值时重新核实。

下文“Arco 含义”是对官方正文的概括；“Motor 落地”是针对网络运维管理端的抽象，不冒充官方逐字要求。不要把官方示例色值、字体或某张示例图直接当作覆盖 Motor 主题的指令，也不要将本文件中示例固化成单一页面模板。

## 1. 设计语言：务实的浪漫主义

Arco 将务实关联到同理心，将浪漫关联到想象力。设计系统先解决常见体验问题、提高协作效率，再为真实业务留下创新空间。

Motor 落地：先确认用户要识别什么对象、判断什么状态、完成什么操作。优先复用已经成立的工作区、组件和交互，让复杂业务更容易理解；差异化必须解释它改善了哪个任务。不要把“浪漫”解释为营销式视觉，也不要把“务实”解释为所有业务都套同一张表。

## 2. 四项价值观：用于决定方案

| 价值观 | Arco 含义 | Motor 落地与取舍 |
| --- | --- | --- |
| 清晰 | 降低不确定性与判断成本，明确层级和目的 | 首屏能辨认当前对象、范围、状态和下一步。区分资源状态、运行风险、采集时效；摘要、筛选和结果的范围能对上。一个提示若不帮助判断或行动，就缩短或移除。 |
| 一致 | 通过稳定的样式、流程和呈现降低重复学习成本 | 对照同菜单的同类任务，复用标题、工具条、筛选、行操作、详情和反馈惯例。统一的是语义与行为，不只是颜色；同名“重置”应有可预测的范围。已有不合理实现不是必须照搬的标准。 |
| 韵律 | 通过重复、对比和排版规律形成自然使用节奏 | 对齐标题、字段、数值与操作，稳定行高和组间距，让相关信息靠近。筛选到结果、列表到详情的顺序符合工作习惯；局部加载不让整页跳动。韵律不要求入场动画或整齐划一的卡片。 |
| 开放 | 允许设计体系随功能和复杂场景适配 | 允许树表、平面列表、诊断详情、配置工具采用不同内容结构，但共用 Motor 的语言与基础组件。差异来自任务和数据关系；不要据此新增第二套主题、布局、权限或配置框架。 |

发生冲突时，先满足业务正确性、用户理解和可操作性，再协调视觉一致。不能为了整齐隐藏风险，也不能为了醒目把所有状态变成主色块。

## 3. 八项设计原则：用于检查行为

| Arco 原则 | Motor 中需要落实的决策 | 可观察的验收问题 |
| --- | --- | --- |
| 及时反馈 | 查询、导入、同步、保存分别展示真实阶段；异步受理和执行完成分开；刷新失败保留已有内容并显示失败 | 操作后能否知道是否开始、是否仍在执行、成功或失败？是否把入队提示写成成功？ |
| 贴近现实 | 按用户工作的对象和顺序组织内容，使用设备、端口、配置、链路等领域用语；实现细节只在帮助诊断时出现 | 标签和动作是否需要用户先理解内部类名、数据库字段或 HTTP 异常？ |
| 系统一致性 | 同类操作复用文案、位置、触发方式、反馈和恢复行为；例外必须有任务依据 | 从相邻页面切过来，用户是否需要重新学习筛选、详情和返回？ |
| 防止错误发生 | 提交前校验，明确目标与范围，防止重复提交；按影响程度使用预览、确认或禁用说明 | 导入前能否看见校验结果？危险操作是否容易误认成普通保存？不要给每个可逆动作增加确认。 |
| 遵从习惯 | 常用动作与当前条件可见；按钮说明真实下一步；保留合理的上下文和返回路径 | 用户是否必须记住隐藏筛选、上一页对象或“下一步”的真实效果？ |
| 突出重点 | 依照扫描顺序组织对象、关键信息和行动；辅助工具降级；按任务决定默认列 | 首屏是否同时出现多个竞争焦点？重要信息是否只能横向滚动或悬浮后才发现？ |
| 错误帮助 | 说明失败对象、影响范围和可执行的恢复动作；保留可恢复输入；技术详情按需展开 | 错误只有代码或 toast 吗？用户能否直接重试、修正输入或检查对应配置？ |
| 人性化帮助 | 优先让结构与命名自解释；再考虑一次性提示、就地常驻帮助和完整文档 | 常见操作是否需要读长说明？复杂字段的帮助是否在做决定的位置？ |

这些原则约束体验结果，不替代后端授权、事务、并发和异步契约。实现规则仍见 `frontend-interaction.md` 与相关领域 reference。

## 4. 样式指南：从角色映射到现有 Token

### 色彩

Arco 区分主色、中性色、功能色和遮罩色。Motor 延续这四种角色，而非复制整套色值：

- 主色：主要动作、选择、焦点与必要品牌识别，使用现有主色及交互态 Token。
- 中性色：文字层级、底面、边界与辅助图标，承担大部分界面结构。
- 功能色：成功、警告、错误等状态；相同语义跨页一致，同时提供文字或图标，避免只依赖颜色。
- 遮罩色：表达模态层与背景的关系，使用 Arco/Motor 已有浮层机制，避免页面自行叠一套遮罩。

Arco 文档中的默认主色 `#165DFF`、遮罩色 `#1D2129` 与 60% 透明度是来源参考，不是 Motor 单页硬编码要求。实现时检查 `--motor-*`、主题映射和组件状态，在深浅主题下保持语义一致；色值相同不代表不同底面上的可读性相同。

### 文字与数字

Arco 建议以少量文字层级建立可读性，优先系统无衬线字体并提供跨平台回退。其通用参考是正文 14px、最小可识别文字 12px、3 至 5 个字号层级、层级差约 2 至 4px；行高默认约 1.4，中文阅读内容需要更充分的行间空间。常用字重为 400、500，英文或数字强调可用 600。

Motor 落地：

- 字体、字号、字重和行高先取现有 Token；不为单页引入 Nunito、Byte Number 或新的字体资源。
- 标题、正文和辅助说明各有稳定职责，用有限的字号与字重区分，避免单行数据里出现过多文字样式。
- 新增关键可读信息以 12px 作为最低设计参考；既有密度或偏好不同，先在真实页面检查，不全局替换，也不通过继续缩字解决溢出。
- 长中文说明按可读性调整行高与段间距；表格、按钮、长文本不共用一个强制行高。官方段间距示例不是所有容器的 padding 标准，也不能直接当成无障碍合规证明。
- 功率、数量、时间等适合稳定数值对齐；IP、序列号、端口标识按原值呈现，不套用数量的千分位格式。截断关键标识时提供完整查看或复制路径。

### 阴影、层级与节奏

Arco 用不同阴影高度表达元素的空间层级，包含四层基础阴影。Motor 采用这一语义：阴影服务浮起关系，背景和细边界服务普通内容分组。文档给出的卡片阴影示例不意味着每个 section 都需要卡片或阴影。

优先使用已存在的 surface、border、radius、space 和 elevation Token。间距通过组内紧密、组间适当分离建立韵律；对齐线与阅读顺序比堆叠容器更重要。此处不从官方样式正文推导其未规定的全局圆角、栅格或动效数值，具体布局仍按 `frontend-ui-patterns.md`。

### 文案样式与用语

Arco 的用语原则是词汇统一、语法正确、文案精炼、通俗易懂、语言友好。Motor 应这样执行：

- 同一对象在菜单、标题、字段、详情和提示中用同一术语；显示文案调整不改变 API 字段或 permission key。
- 操作文案优先“动词 + 对象”，准确说明实际效果，例如“预览导入”“开始同步”；避免“确定”“下一步”承担不明确的业务含义。
- 状态与统计包含必要单位和范围，检查 0、1、大数、负值、缺失值与长名称；缺失不显示为真实零值。
- 日期时间默认按项目统一 formatter 和时区语义呈现，优先 24 小时制；采集时间、执行时间和相对时间不混为一谈。
- 数量用 locale-aware 格式化；量纲、百分比、范围和正负号统一，不能为了紧凑丢失判断所需的单位或精度。
- 中文与英文、数量之间合理留空格，中文全角标点旁不额外加空格；完整英文句子使用英文标点。协议值、URL、代码、IP 和标识符保持原样。
- 默认提示表达用户可以做什么，避免训斥、无依据的绝对承诺和冗长客套；错误与安全限制需要准确表达，不能为了友好淡化影响。
- 中英文 locale 同步，检查窄屏换行与标点位置。省略号不能替代对关键动作、风险原因的完整表达。

## 5. 在现有页面中执行

开始改造时，用当前页面和一至两个同类页面回答：

1. 哪个任务受影响？是识别对象、判断状态、执行动作还是恢复错误？
2. 偏离发生在哪一项价值观或原则？用实际画面或行为说明，避免只说“不够高级”。
3. 哪些共用组件、Token 和行为已经满足需求？哪个差异有真实业务理由？

然后按责任调整内容结构、状态或局部组件。重构可以重新组织内部代码，但不能为了视觉统一丢失正确业务能力，也不能把某个表格的列顺序变成全项目规则。

交付时用结果验证设计依据：同类控件是否可预测、主次是否可扫描、状态反馈能否恢复、深浅主题及窄屏是否可用。按照 `frontend-experience.md` 的浏览器矩阵检查相关状态；源码、工程门禁和真实渲染分别报告。审美判断不得仅由 build 成功代替。
