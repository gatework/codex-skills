# Rails 信条的项目应用

用于模块功能设计、职责拆分、公共抽象、配置与依赖选择，以及对既有架构的纠偏。

来源：[David Heinemeier Hansson：Rails 信条（简体中文）](https://rubyonrails.org/doctrine/zh_cn)。以下规则是结合 Motor 现有技能契约推导的项目方法，不是原文逐条翻译，也不是对当前代码实现的验证。原文的九项价值主张提供判断方向；安全、数据和发布边界仍按本技能对应 reference 执行。

## 从信条到设计判断

| 原文主题 | 在 Motor 中的应用 | 容易误用的边界 |
| --- | --- | --- |
| 程序员的幸福最大化 | 让维护者容易找到入口、理解业务、验证修改；评价一次完整改动需要掌握多少隐含知识 | 个人语法偏好不能成为全仓重写的理由，也不等于只优化键入量 |
| 约定优于配置 | 常规命名、资源操作和响应沿用项目约定；真实业务差异在局部明确表达 | 不为每个差异增加 setting，也不把独特状态流塞进通用 CRUD 模板 |
| 主厨精选 | 把 Rails、PostgreSQL、Sidekiq、Vue、Arco 作为协作整体评价；替换组件要计算接入和长期维护成本 | 单库指标领先不足以证明替换整个系统中的既有能力合理 |
| 多元化的设计模式 | 按状态、职责与副作用选择 model、service、query、纯函数或组件 | 不强制每个操作都建立 service/repository/DTO 全套层级 |
| 推崇优美的代码 | 名称和调用顺序能读出业务意图，查询与命令清楚，重要副作用可追踪 | 短代码、隐式 DSL 和少文件不自动意味着容易理解 |
| 提供实用工具 | 根据实际收益使用 Concern、Ruby 表达力和框架扩展点，说明宿主依赖与影响范围 | 不一律禁用有力工具，也不因框架允许就接受无边界的全局修改 |
| 重视整合系统 | 优先在现有应用内形成清楚模块，让规则与数据有统一归属 | 模块化不要求独立部署；也不据此推翻现有 Rails API + Vue 架构 |
| 进步比稳定重要 | 当旧设计持续增加成本时允许演进，用收益、迁移路径和验证决定改动 | 不把价值主张解释成任意破坏持久数据、外部 API 或队列兼容的许可 |
| 包容并重 | 允许有证据的局部例外；用业务结果和维护成本评判方案 | 不因原文作者的个人偏好替换 RSpec，也不把例外扩成第二套基础设施 |

## 模块先围绕用户任务成立

设计一个功能时，先把这些信息写清楚，简单任务可以用几句话完成：

- 谁在什么场景下完成什么动作，怎样才算完成；
- 哪些数据是权威事实，谁可以修改，哪些只是派生展示；
- 动作的前置条件、状态变化和不可破坏的不变量；
- 失败、重复执行、并发及异步完成后，用户怎样看到真实结果；
- 现有哪个入口和领域能力负责该动作，确实缺少什么。

据此设计最小的端到端功能，再决定文件拆分。页面名称、数据库表数量、代码行数都不能单独决定模块边界。同一用户任务可以跨多个技术层，但业务规则应有明确归属。

例如设计“批量导入”：先确定预览与提交是否分离、重复记录如何处理、部分失败是否允许、谁有写权限、结果如何回看。随后复用解析、领域写入和页面反馈能力；不能先搭建通用导入引擎，再要求业务适应引擎。这里是设计示例，不表示 Motor 当前已具有该流程。

## 代码组织服从职责

- 关联、validation、持久化不变量和小型原子操作可以自然地放在 Active Record model 中；不为了隔离数据库的形式纯粹性机械增加 repository。
- 跨模型事务、明确业务阶段或外部副作用需要编排时使用 service；简单保存不必先经过一个仅转发参数的 service。
- 无状态的转换用纯函数或局部方法；复杂筛选才考虑 query，不能把每条 scope 包成类。
- Concern 可以表达单个 model 内可独立理解的能力，不要求必须有第二个宿主。方法应围绕同一职责，并能说明依赖的字段、关联、回调与方法；仅把大文件切碎不构成提取理由。
- 可跨调用方复用的公共抽象仍遵守 `engineering-quality.md` 的门槛。单个模块内部的职责分解与建立公共框架是不同决策。
- 前端页面编排任务；有独立交互、状态或清晰展示职责时拆组件/composable。能从已有状态推导的值不另建 store，也不为了目录对称增加空壳。

检查抽象是否有效：沿一次真实调用追踪输入、状态和失败。若新层只增加跳转，仍需了解所有底层细节才能修改，则应收缩；若它让不变量、生命周期或测试边界更清楚，则有保留价值。

涉及 Concern、元编程或 monkey patch 时先检查官方扩展点及局部实现能否满足。确需改变全局行为时，说明受影响调用方、加载与升级假设、回归证明和移除条件；不要把跨系统 I/O 藏进隐式回调。框架原语的具体行为以当前版本文档和测试为准。

## 默认值与例外的成本

新增选项前判断差异来自哪里：

1. 所有用户都需要同一行为：采用正确默认值。
2. 差异来自实体或业务状态：显式建模，避免靠全局开关表达领域事实。
3. 存在真实、长期并存的运维策略：才考虑配置，并定义作用范围、默认值和维护责任。

偏离约定时留下简短理由：哪个具体场景无法表达，现有原语为何不足，局部例外如何控制影响，什么证据说明收益值得成本。不要要求普通 CRUD 为遵循约定重复撰写设计报告。

选型和拆服务同样按整条链路计算成本：认证、序列化、网络失败、重试、数据一致性、部署、观测和排障。只有实际的独立扩缩容、隔离或生命周期需求足以抵偿这些成本时，才推进进程或服务拆分。

## 偏离约定的轻量记录

确需偏离既有约定时，在 PR 描述或代码旁用四行写清，不需要单独的设计文档：

```text
场景：哪个具体需求无法用现有约定表达
原因：现有原语为何不足（附证据：代码位置、测试、失败序列）
影响：例外的作用范围，哪些调用方受影响
退出：什么条件下可以回到约定或删除例外
```

普通 CRUD 遵循约定，不需要为“遵循”写这段记录。通用的思考方式见 [engineering-mindset.md](engineering-mindset.md)。

## 演进与验收

“保持兼容”约束发布过程，不要求永久保留错误设计；“推动进步”要求可解释收益，不意味着追逐每个新工具。涉及持久或外部契约时，按 `engineering-quality.md` 与 `testing-delivery.md` 安排兼容窗口、迁移验证和旧路径退出条件。

交付前结合任务检查：

- 新维护者能否从入口找到业务规则和状态归属？
- 是否减少了无谓选项、重复知识或隐藏耦合，而不是仅减少行数？
- 常规路径是否复用约定，业务例外是否清楚且局部？
- 用户能否完成任务并理解失败、等待和最终结果？
- 是否用对应测试或运行证据证明行为，且未把架构偏好当成正确性证据？

具体后端边界见 [backend-domain.md](backend-domain.md)，抽象与迁移见 [engineering-quality.md](engineering-quality.md)，前端状态与反馈见 [frontend-interaction.md](frontend-interaction.md)，验证见 [testing-delivery.md](testing-delivery.md)。
